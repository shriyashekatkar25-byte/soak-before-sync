01 · The decision

Live sync, or soak first?

Shared skills are instructions that other companies' agents read and act on. A provider's bad edit doesn't stay in one workspace: it reaches every recipient's agents. I'm playing the PM who owns skill distribution, and I have one default to set.

the customer problem

A data team installs a Marketplace skill (say, "reconcile monthly revenue") and builds an agent on it. The provider ships a fix on Tuesday, and on Wednesday the agent starts filing wrong numbers. Recipients can't edit the skill, because it's read-only, so they're stuck until the provider notices.

— "I didn't change anything!"

the proposed change

Add a soak window: a new skill version goes live right away for an opt-in canary ring and for the provider's own evals. It reaches everyone else after S hours unless a break is detected first. Security fixes can skip the line.

Default to set: S hours · canary ring size · security fast-lane on/off

success metric

Broken agent-hours per recipient per quarter drops by at least 50% compared with live sync. A broken agent-hour is one hour in which a recipient's agent runs on a version that later gets rolled back.

guardrails

Broken agent-hours / recipient / quarter≤ 1.0 h
Recipients hit by ≥1 bad version / quarter≤ 8%
Improvement delay (soak length)≤ 72 h
Security-fix delay, P90≤ 24 h

stakeholders

  • Skill providers: want fixes out fast and few angry tickets
  • Recipient platform teams: want agents that don't change underneath them
  • Marketplace & sharing eng: own the version pipeline
  • Security: need patches to land quickly
  • Field / support: absorb the "my agent broke" escalations

why it's hard

Every hour of soak catches more bad versions, but it also delays every good one. Meanwhile the canary ring takes the hits for everyone else. Providers vary too: a careful team and a move-fast team behave nothing alike. Averages hide all of this, so I simulate it.

02 · Simulation room

The rain pond

Each drop is one simulated skill update landing on a recipient pond. Most ripple out harmlessly. Bad versions that the soak caught close up into lotus buds. Bad versions that escaped leave red rings. Each run simulates thousands of provider-quarters from a seed, so every run is reproducible.

04 · The math, from my Monte Carlo course

Composition: build hard randomness from easy pieces

Chapter 5 of Stats 102C is about building a complicated random variable out of simple ones you already know how to sample. This model uses three of those moves.

mixtures

Providers aren't one population. To draw a provider, first flip a weighted coin to pick its component (careful or move-fast), then sample from that component's own ship and break rates. The overall distribution is the weighted blend, and its tails come from the minority component.

f(x) = w·f_fast(x) + (1−w)·f_careful(x)

Product read: if 25% of providers cause most breaks, a per-provider policy beats a global one.

convolutions

A sum of independent pieces has a distribution that is their convolution. Adding up 13 weekly "did they ship?" coin flips gives a Binomial count of updates. Adding up the waits between user reports, then the fix time, gives a Gamma-shaped time to rollback.

T = E₁ + E₂ + E_fix, Eᵢ ~ Exp(mean)

Product read: needing more reports to confirm a break pushes the whole exposure curve to the right.

Box-Muller

Two uniforms become two independent normals: a radius √(−2 ln U₁) and an angle 2πU₂. I use this to draw each good update's quality lift, which tells me how much value a long soak holds back from customers.

Z = √(−2 ln U₁) · cos(2π U₂)

Product read: soak isn't free. Every hour delays real improvements for everyone.

05 · How I'd run it on real data

Swap the priors for telemetry

The simulation's inputs (ship rate, break rate by provider type, report rate, time to fix) should all come from logs. Table names below are illustrative.

SQL: fit the inputs

-- break rate and time-to-rollback by provider cohort
WITH versions AS (
  SELECT v.provider_id, v.skill_id, v.version_id,
         v.published_at, r.rolled_back_at,
         p.cohort  -- 'careful' | 'move_fast' from ship cadence
  FROM sharing.skills.version_events v
  LEFT JOIN sharing.skills.rollbacks r USING (version_id)
  JOIN sharing.skills.provider_cohorts p USING (provider_id)
  WHERE v.published_at >= current_date() - INTERVAL 180 DAYS
)
SELECT cohort,
  count(*)                                  AS versions,
  avg(CAST(rolled_back_at IS NOT NULL AS INT)) AS break_rate,
  percentile_approx(
    timestampdiff(MINUTE, published_at, rolled_back_at)/60.0, 0.5
  )                                         AS p50_hours_to_rollback
FROM versions
GROUP BY cohort;

Python: sweep the soak

import numpy as np
rng = np.random.default_rng(2026)
inputs = spark.table("sharing.skills.sim_inputs").toPandas()

def broken_hours(S, n=20_000, ring=0.10):
    fast = rng.random(n) < inputs.w_fast[0]          # mixture
    p_break = np.where(fast, inputs.p_fast[0], inputs.p_careful[0])
    bad = rng.random(n) < p_break
    t_soak = rng.exponential(inputs.m[0]/ring, (n, 2)).sum(1)  # convolution
    caught = bad & (t_soak < S)
    t_live = S + rng.exponential(inputs.m[0], (n, 2)).sum(1)
    fix = rng.exponential(inputs.fix_mean[0], n)
    exposed = np.where(bad & ~caught, t_live + fix - S, 0)
    return exposed.mean()

grid = [0, 12, 24, 48, 72, 96]
print({S: round(broken_hours(S), 2) for S in grid})
